## Механика, которую надо решить

### Переименование и ссылки

Ссылки хранятся строкой в страницах, partials, components и `site.json`. Переименование это атомарная правка нескольких мест.
- Редактор держит документ в памяти и автосохраняет (`autosave.ts`). Если сервер перепишет JSON на диске сам, следующее автосохранение вернёт старый путь. Поэтому переименование идёт через клиент: сервер переименовывает файл, клиент одним патчем обновляет документ (это даёт один шаг Ctrl+Z). При сбое файл возвращается.
- Надо ловить все места: `src`, `srcset`, `style="...url(...)"`, `meta.ogImage`, `favicon`, шрифты. Единую функцию «собрать ссылки на ассеты» стоит вынести в `packages/core` и использовать и в экспорте (сейчас там `URL_ATTRS` и `ASSET`), и в библиотеке, чтобы правила не разошлись. Она же даёт «используется на страницах X».
- Публичный URL в экспорте меняется (`assets/img/old-960.webp` на `new-960.webp`). Для нового сайта не важно. Для уже опубликованного на Bitrix ломает внешние ссылки и индексацию картинок.

### Удаление, undo и страницы, которые ссылаются на файл

- Сейчас Ctrl+Z вернёт в документ ссылку на уже удалённый файл. Варианты: (a) переносить в `assets/.trash/`, undo и «вернуть» работают; (b) запрещать удалять используемое; (c) удалять с предупреждением, на странице остаётся битая картинка (экспорт предупредит `Could not process image`, но не остановится).
- Предлагается (a)+(c): корзина в проекте (исключить из списка, из экспорта и из git), предупреждение со списком страниц.
- Саму операцию «удалить» в историю документа не класть: она меняет не документ, а файлы. Отменяется кнопкой «Вернуть» в уведомлении или из корзины.

### Где хранить метаданные

| Вариант | Плюсы | Минусы |
| --- | --- | --- |
| Файл рядом `assets/photo.jpg.json` | Едет вместе с файлом, не раздувает `site.json` | Захламляет папку, нужно скрывать от списка и экспорта, при ручном переименовании в проводнике теряется |
| Один `assets/_library.json` | Один файл, легко искать, папки и теги просто поля | Конфликты в git при параллельных правках, мусорные записи после ручного удаления (нужна сверка при открытии) |
| Внутри `site.json` | Уже есть валидация (`validate.ts`) и автосохранение | Раздувает и шумит в диффе, метаданные файлов не относятся к сайту как документу |

Рекомендация: один `assets/_library.json`, ключ = имя файла (`alt`, `folder`, `tags`, позже `width`, `height`). Метаданные необязательны: проект без файла работает как сейчас, отсутствующие записи игнорируются.

## Варианты

### A. Менеджер файлов поверх текущей модели (путь = имя файла), размер M

Диалог «Ассеты»: сетка, поиск, drag and drop, переименование через патч документа, удаление в корзину с предупреждением, «неиспользуемые», PDF в `ALLOWED`. Метаданные в `assets/_library.json`.
- Плюсы: без миграции формата, проекты остаются плоскими и читаемыми, хорошо живут в git и при ручной работе с папкой.
- Минусы: переименование меняет публичный URL.

### B. A плюс папки, теги, alt по умолчанию, «заменить файл везде», размер L

Виртуальные папки (поле в метаданных, на диске плоско, пути не меняются). Alt файла подставляется при вставке. Замена файла с тем же путём (кеш WebP сам обновится: `isFresh` сравнивает mtime, а `dist/` и так пересобирается).
- Плюсы: закрывает весь список.
- Минусы: больше UI. Alt по умолчанию требует решения: копировать в узел или держать живую связь.

### C. Постоянные id ассетов, размер L и выше

Узлы хранят `asset:<id>`, путь разрешается при экспорте. Переименование и перемещение бесплатны.
- Плюсы: как у Webflow и Wix.
- Минусы: миграция страниц, пресетов и вставки HTML, JSON перестаёт быть читаемым, больше мест для ошибок. Для локального инструмента с папкой в git избыточно.

## Рекомендация

**A как MVP, затем пункты B по мере нужды. C не делать.**

- MVP: диалог с сеткой и поиском, drag and drop нескольких файлов, удаление с «используется на...» и корзиной, список неиспользуемых с массовой очисткой, переименование одним патчем документа, PDF и прочие файлы для ссылок, `_library.json` пока только для alt.
- Потом: папки/теги, «заменить файл везде», размеры в px, предупреждение о тяжёлых файлах, поиск дублей по хэшу, миниатюры с сервера вместо оригиналов.

6. Нужна ли «заменить файл везде» в первой версии? Типовой сценарий: обновили логотип.
7. Где открывать библиотеку: отдельный диалог, боковая панель, только в пикере картинки, или везде?
8. Шрифты: оставить в диалоге шрифтов (как сейчас) или показывать в библиотеке только как «используется шрифтами»?
9. Сколько ассетов в типичном проекте? От этого зависят пагинация и серверные миниатюры.

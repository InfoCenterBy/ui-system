# Генерация секции по описанию

Проработка: варианты решения и вопросы для обсуждения. В работу — после решения. Код не менялся.

## Как работает сейчас

| Что | Где | Как |
| --- | --- | --- |
| Пресеты секций | `packages/blocks/src/sections/<категория>/*.html`, список и метаданные в `sections/index.ts` | Около 85 HTML-файлов по категориям (hero, features, pricing, faq, gallery, footer и т.д.). `import.meta.glob` подтягивает HTML, `presetMeta` задаёт `id`, `name`, `category`, `group`. Пресет это одна корневая секция (проверка в `packages/core/src/html.ts`: ровно один корневой элемент). |
| Разметка для редактора | `data-edit="text\|rich\|image\|link"`, `data-repeat`, `data-label` | Пример `hero-image.html`: `<h1 data-edit="text">`, `<p data-edit="rich">`, `<img data-edit="image">`, `<a data-edit="link">`. `data-repeat` помечает повторяемые элементы (карточки, пункты). Эти атрибуты съедаются парсером (`html.ts`) и не попадают в экспорт. |
| Вставка | `packages/core/src/insert.ts` `prepareInsert` | Глубокая копия: уникальные `id`, `name` у radio/checkbox, якоря, обновление ссылок на `#id`, подмена демо-картинок `img.daisyui.com` на локальный `placeholder.svg`. |
| Скрипты | `server/export.ts` `takeScripts` | Инлайн-скрипты секций уходят в `assets/site.js`. Это относится и к пресетам, и к блоку «Custom» (`sections/custom`). |
| Классы | `server/classes.ts`, `/api/classes/components`, `packages/core/src/classes.ts` | Индекс классов daisyUI собирается из CSS (`parseRules`, `classesFromRules`), используется для подсказок в поле классов (`ClassField.tsx`). Утилиты Tailwind группируются в `UTILITY_GROUPS`. |
| Стили на выходе | README | Один Tailwind+daisyUI билд на сервере: канвас и экспорт совпадают; в `site.css` попадают только используемые классы. Тема и шрифты берутся из `site.theme` и `site.fonts`. |
| Внешнего AI в проекте нет | поиск по `apps/builder` | Ни SDK, ни ключей. Билдер локальный, работает офлайн. |

Вывод: у нас уже есть всё, что нужно для безопасной генерации: ограниченный словарь (daisyUI/Tailwind), формат разметки с `data-edit`, функция вставки, парсер, который строит редактируемое дерево. Не хватает только источника разметки и валидатора.

## Варианты

### A. Подбор из готовых пресетов по описанию, без AI, размер S-M

Описание разбивается на ключевые слова (русский и английский: «цены», «тарифы» -> `pricing`, «команда» -> `team`, «вопросы» -> `faq`), по категориям и названиям пресетов ищется подходящий, текст-заглушка не меняется или заполняется шаблонными строками. Можно добавить теги и синонимы в `presetMeta`.
- Плюсы: офлайн, бесплатно, мгновенно, результат всегда валиден и редактируем, стили ровно те.
- Минусы: это по сути умный поиск по каталогу, а не генерация; текст нужно писать вручную; нестандартную секцию не получить.
- Оговорка: сейчас в билдере каталог секций и так просматривается. Ценность A лишь в быстром поиске по описанию.

### B. LLM пишет HTML в формате пресета, размер L

Модель получает системную подсказку: формат пресета, правила `data-edit`/`data-repeat`, 3-5 примеров пресетов из нужной категории, список разрешённых классов и тему/язык сайта, и возвращает один HTML-фрагмент. Сервер валидирует, санитизирует и вставляет через `parseHtml` и `prepareInsert`.
- Плюсы: настоящая «секция под задачу», тексты сразу по теме, редактируемость через `data-edit`.
- Минусы: нужен ключ API и сеть, стоимость, непредсказуемость, нужна валидация и ретраи.

### C. Генерация по скриншоту или картинке, размер L-XL

То же, что B, но на входе картинка (макет или скриншот чужой секции). Нужна модель с поддержкой изображений.
- Плюсы: быстрый старт от макета.
- Минусы: сложнее всего, плохая точность по размерам и тонкому оформлению, вопросы авторских прав на чужой дизайн, дороже по токенам (изображение на входе). Откладывать.

### D. Только тексты, размер S

Пользователь выбирает готовый пресет, описывает бизнес, модель возвращает JSON значений для всех `data-edit` (заголовок, текст, пункты `data-repeat`), и они подставляются в слоты.
- Плюсы: самое безопасное (HTML не генерируется вообще, значения экранируются), самый дешёвый запрос, результат гарантированно валидный и в нужной вёрстке, нет проблемы классов, скриптов и картинок.
- Минусы: форма секции не меняется, только содержимое.

## Техническая часть для B и D

### Модель и API

Для генерации разметки, где важны структура и соблюдение формата: `claude-sonnet-5-5` как рабочая лошадка, `claude-haiku-5-5` для режима D (только JSON с текстами) и быстрого/дешёвого варианта, `claude-opus-5-5` как опция «лучшее качество» для сложных секций. Точные цены и лимиты перед реализацией нужно сверить с текущим прайсом (по памяти не фиксируем). Вызов через Anthropic Messages API, structured output (JSON-схема) для D, обычный текстовый ответ с блоком ```html для B.

### Где хранится ключ (локальный инструмент)

| Способ | Плюсы | Минусы |
| --- | --- | --- |
| Переменная окружения `ANTHROPIC_API_KEY` при запуске `pnpm builder` | Ключ не попадает ни в проект, ни в git, привычный способ | Неудобно для нетехнического пользователя |
| Файл настроек пользователя вне проекта (`%APPDATA%`/`~/.config/…`), поле в диалоге «Настройки» | Удобно, ключ не едет с проектом в git | Хранится открытым текстом на диске, нужно ограничить права |
| В `site.json` или файлах проекта | Просто | **Нельзя**: проект лежит в git, ключ утечёт |

Вызов делает только сервер билдера (`apps/builder/server`), ключ в браузер не отдаётся. Рекомендация: переменная окружения плюс настройка пользователя вне проекта, никогда внутри папки проекта.

### Стоимость секции (оценка порядка, считать по текущему прайсу)

Запрос B: системная подсказка + примеры + индекс классов около 6-10 тыс. входных токенов, ответ около 1-2,5 тыс. выходных токенов. Кеширование статической части подсказки (prompt caching) снижает вход при повторных запросах. Для D: около 1-2 тыс. входных и 300-800 выходных токенов. Порядок: для Sonnet секция B стоит доли цента-несколько центов, для Haiku D существенно меньше. Конкретные цифры нужно посчитать по прайсу на момент реализации и показывать в интерфейсе оценкой.

### Офлайн

Генерация недоступна без сети и без ключа. Остальной билдер не затрагивается: кнопка «Сгенерировать» скрыта или неактивна с понятной причиной. Вариант A работает всегда и может служить запасным путём.

### Валидация и санитизация (для B)

1. Парсинг через наш `parseHtml`; ровно один корневой элемент (как для пресетов).
2. Белый список тегов и атрибутов. Убрать `<script>`, `<iframe>`, `<object>`, `<embed>`, `<link>`, `<style>` (внутренние стили генерировать нельзя), атрибуты `on*`, `javascript:` в `href`/`src`, `srcdoc`, `formaction`.
3. Скрипты: по умолчанию запретить совсем. Для интерактива использовать только daisyUI-компоненты на CSS (`collapse`, `modal`, `tabs`) или существующие механизмы билдера, как в пресетах. Если нужны скрипты, только через блок «Custom».
4. Картинки: внешние `src`/`url()` заменить через `prepareInsert` с `imageSrc` на `placeholder.svg`; модель вообще не должна ставить внешние адреса. Иконки только инлайн-SVG или из наших пресетов.
5. Классы: разбить через `splitClasses` и `parseClass` (`packages/core/src/classes.ts`), проверить по индексу (`/api/classes/components` для daisyUI, `UTILITY_GROUPS`/Tailwind для утилит). Неизвестные классы удалить или запросить исправление у модели, максимум 1-2 ретрая, потом отдать результат без плохих классов с предупреждением. Произвольные значения `[...]` разрешать ограниченно.
6. Цвета только через токены темы (`bg-base-200`, `text-primary`, `btn-primary`), а не `#hex`/`bg-blue-500`, иначе секция не подстроится под тему сайта. Валидатор может подсвечивать такие классы.
7. Шрифты: ничего не указывать; секция наследует `font-sans`/`font-heading` темы из `site.fonts`. Запретить `font-[...]` и `style="font-family"`.
8. Размер: лимит на длину HTML и глубину дерева.

### Как результат становится редактируемым

- Подсказка требует расставить `data-edit="text|rich|image|link"` на всех местах с контентом и `data-repeat` на повторяющихся элементах, точно как в примерах.
- Валидатор проверяет, что у каждого заметного текстового узла и картинки есть `data-edit`; чего не хватает, можно проставить автоматически эвристикой (заголовки и `p` -> `text/rich`, `img` -> `image`, `a` -> `link`).
- Дальше то же, что с пресетом: `parseHtml` -> дерево -> `prepareInsert` -> вставка. Секция попадает в страницу как обычная (`section.preset` будет `custom`/`ai`, `locked` по правилам), редактируется на холсте и в панели.
- Хорошая практика: показывать результат как предпросмотр с кнопками «Вставить» и «Ещё вариант», не вставлять сразу в страницу. Вставка одним шагом undo.
- Сохранять промпт в метаданных секции не обязательно.

## Вопросы владельцу

1. Нужен ли вообще внешний AI в локальном инструменте, или достаточно умного поиска по пресетам (вариант A)?
2. Готов ли платить за API и вести собственный ключ? Какой бюджет на секцию/месяц допустим, показывать ли оценку стоимости перед запросом?
3. Что важнее: заполнить текстами готовую вёрстку (D) или получать новые вёрстки (B)?
4. Язык результата: русский по умолчанию или язык сайта (`site.lang`)?
5. Данные о бизнесе уходят в стороннее API (описание сайта, тексты страниц). Допустимо ли это для ваших проектов? Передавать ли контекст сайта (название, тон, соседние секции)?
6. Где хранить ключ: переменная окружения, настройка пользователя вне проекта, или оба?
7. Скрипты в сгенерированных секциях: запретить полностью (рекомендуется) или разрешать через блок «Custom»?
8. Картинки: оставлять placeholder или генерировать описания alt и подбирать из библиотеки ассетов?
9. Нужна ли генерация нескольких вариантов («Ещё вариант») и сохранение удачных как своих пресетов/компонентов?
10. Нужна ли генерация по скриншоту хоть когда-нибудь (вопрос авторских прав на чужой дизайн)?
